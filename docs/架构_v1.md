**DevFlow AI 不能继续依赖 Claude Code 自己记住 Skill 中的每一条规则，而应该逐步把关键执行规则从提示词约束升级为工作流引擎的执行机制。**

但我不建议现在推倒重构。你已经有 Agent Manager、SQLite、HITL、DAG 调度、Verifier、Reporter、Notifier 等组件，应该以这些现有能力为基础，逐步建立真正可靠的 Workflow Core。

我的总体建议是：

**短期先修复 Skill 执行可靠性，中期完成 Workflow Core，长期发展为多 Agent、多 Provider 的可插拔研发自动化平台。**

当前阶段

## **二、Phase 1：优先建设 Workflow Core**

这是最重要的一阶段。

目前的核心问题是：Skill 既承担流程说明，又承担流程控制，还承担状态推进。这种方式对 LLM 的执行稳定性要求太高。

建议明确职责：

| 模块           | 应承担的职责                           |
| -------------- | -------------------------------------- |
| Skill          | 告诉 Agent 任务怎么做、各阶段产出什么  |
| Workflow Core  | 决定工作流处于什么状态、下一步执行什么 |
| DAG Scheduler  | 根据依赖关系调度可执行节点             |
| Agent Adapter  | 启动、管理和监控 AI Coding Agent       |
| Human Decision | 创建、等待、接收和恢复人工决策         |
| Reporter       | 回写禅道任务进度和状态                 |
| Notifier       | 发送钉钉通知                           |
| SQLite         | 唯一权威执行状态                       |

### **1. 统一工作流状态机**

建议先统一这些状态：

**READY** — 可以开始执行

**RUNNING** — 正在执行

**WAITING****_****HUMAN**

等待人工决策

**RETRYING**

正在重试

**VERIFYING** — 验收中

**COMPLETED** — 验收通过，工作流完成

**FAILED / CANCELLED** — 失败或用户取消

这里要特别注意：

`WAITING_HUMAN` 不应该成为所有节点的全局阻塞状态。它应该首先是节点级状态，工作流本身可以同时存在等待节点和正在执行的独立节点。

### **2. 建立统一的阶段生命周期**

建议每个阶段统一经过：

```
Stage Started
    ↓
Agent Execution
    ↓
Stage Result Persisted
    ↓
Verification
    ↓
Progress Report
    ↓
Notification
    ↓
Next Stage Dispatch
```

遇到人工决策时：

```
Decision Required
    ↓
Create Human Decision
    ↓
Persist WAITING_HUMAN
    ↓
DingTalk Notification
    ↓
Continue Independent Nodes
    ↓
Receive Decision Callback
    ↓
Restore Original Workflow
```

这些步骤应该由 Core 负责组织，而不是要求 Agent 自己记住每一步。

### **3. 把关键规则变成代码约束**

我建议优先固化五项规则：

| 规则                             | 应由谁保证            | 是否依赖 LLM 自觉 |
| -------------------------------- | --------------------- | ----------------- |
| 阶段完成必须保存结果             | Workflow Core         | 否                |
| 阶段完成必须触发进度回写         | Reporter / Core       | 否                |
| L3 决策必须创建持久化请求        | Human Decision / Core | 否                |
| 未批准节点不能执行               | Scheduler             | 否                |
| 工作流不能在仍有可执行节点时结束 | Workflow Core         | 否                |

Skill 仍然需要告诉 Agent 如何分析需求、设计方案、编写代码、执行测试，但不再承担这些基础流程保障职责。

例如，Agent 完成设计后，不应该自己决定“要不要通知钉钉”，而应该向 Core 提交阶段结果，由 Core 根据阶段定义和审批策略判断是否需要发起决策。

这会大幅减少类似 #3434 的问题。

## **三、Phase 2：Agent Adapter 和 Provider 抽象**

Phase 1 稳定后，再解决不同 Agent 和外部系统之间的兼容问题。

### **1. Agent Adapter**

**Workflow Core**

统一调度、状态、恢复、验收

**Claude Code**

优先实现

**Codex**

后续扩展

**OpenCode**

后续扩展

Adapter 统一提供基本能力：

- 启动 Agent 任务。
- 传入工作目录、提示词和任务上下文。
- 获取运行状态。
- 获取执行结果和错误信息。
- 处理中断、超时和恢复。
- 声明自身支持的能力。

这里不要假设不同 Agent 都具备相同能力。例如，有的支持会话恢复，有的支持工具权限控制，有的支持多 Agent 协作。应该通过 capabilities 声明，而不是强行统一。

**实施顺序：先把现有 Claude Code 调用封装成 Adapter，不改变现有执行行为；验证通过后再考虑 Codex 和 OpenCode。**

### **2. Provider**

Provider 负责外部系统集成：

| Provider           | 负责内容                          |
| ------------------ | --------------------------------- |
| Project Management | 禅道任务查询、进度、finish、close |
| Notification       | 钉钉消息和人工决策通知            |
| CI/CD              | Jenkins 构建、部署                |
| Git                | 仓库、分支、提交、PR/MR           |

其中 Jenkins 必须保留人工确认机制：Agent 可以准备构建或部署请求，但未经用户确认不能触发真实部署。

这些 Provider 不需要同时开发。先把当前已经运行的禅道、钉钉集成逐步接入统一接口即可。

## **四、Phase 3：可靠性和长任务能力**

我认为这一阶段有三项能力特别重要。

**1. 可靠恢复**

SQLite 继续作为唯一权威状态，记录：

- workflow 和 task 状态
- DAG 节点状态
- Agent 执行记录
- 人工决策请求
- 执行事件
- 阶段结果和恢复上下文

发生进程崩溃、电脑重启、Agent 退出时，能够根据 SQLite 恢复，而不是依赖终端上下文。

**2. 事件驱动通知**

建议在现有 Notifier 上增加轻量级的可靠投递机制：

```
Workflow Event
    ↓
SQLite 持久化事件
    ↓
Notification Dispatcher
    ↓
DingTalk Provider
    ↓
发送结果记录
```

这样即使钉钉暂时不可用，也不会因为一次发送失败就丢失通知事件。

不用现在引入 Kafka、RabbitMQ 等消息中间件。SQLite 对目前的单机或内网部署已经足够。

**3. 长任务自动恢复**

最终希望达到：

- Claude Code 执行到一半异常退出，可以恢复。
- 子 Agent 失败，能够识别失败原因并按策略重试。
- 人工决策等待期间，独立节点继续运行。
- 机器重启后，未完成工作流可以恢复。
- 失败、等待、完成等事件自动通知钉钉。
- 验收通过后自动 finish/done，满足关闭条件后自动 close。

这些能力应该以真实故障模拟测试验证，而不是只看单元测试数量。

## **五、我建议的实际实施顺序**

不要同时启动多个大改造。我建议按以下顺序推进：

| 阶段 | 工作内容                         | 验收标准                               |
| ---- | -------------------------------- | -------------------------------------- |
| 0.6  | 完成本次四项最小修复             | Skill 不再对话阻塞，钉钉和进度回写正常 |
| 1.1  | Workflow Core 接管工作流生命周期 | 状态推进、阶段结束、结束条件统一       |
| 1.2  | Core 接管 HITL 和恢复            | 决策等待、独立节点继续、回调恢复       |
| 1.3  | Core 接管阶段回写和通知          | 阶段完成自动回写，通知可靠             |
| 1.4  | Claude Code Adapter              | 现有 Claude Code 工作流完整接入        |
| 2.1  | Provider 统一接口                | 禅道、钉钉、Jenkins、Git 逐步接入      |
| 2.2  | 多 Agent 扩展                    | 评估接入 Codex、OpenCode               |
| 3.0  | 轻量管理平台                     | 任务、运行记录、决策和执行监控         |

### **这里有三个设计决策，我建议现在就确定**

**决策一：SQLite 继续作为唯一状态中心。**

不要再引入第二套状态系统，也不要为了架构升级迁移现有 Agent Manager 的全部代码。优先复用现有表和状态管理器，只有确实无法满足的地方才增加字段或表。

**决策二：工作流执行和 Agent 执行分离。**

Workflow Core 管理工作流，Agent Adapter 管理 Agent 进程。

例如 Claude Code 崩溃，不应该直接导致工作流状态丢失；工作流等待人工决策，也不应该被认为是 Agent 执行失败。

**决策三：Skill 继续保留，但逐步变轻。**

不要废弃现有 Skill。它仍然是 Agent 的工作方法和研发规范载体，只是逐步将流程控制权交给 Core。

## **六、跨平台和技术选型**

重点避免：

- 将 `cmd.exe`、PowerShell 写死在核心流程中。
- 将 Windows 盘符路径写死在状态数据中。

我建议把后续改造正式定为：

# **DevFlow AI · Phase 1**

**Workflow Core 渐进式改造**

目标：让工作流引擎而不是 LLM 自身决定执行状态、节点推进、人工等待和任务结束。

**第一批只做五件事：**

2. 定义 Workflow Core 最小接口和生命周期。
3. 将现有 DAG 调度接入统一生命周期。
4. 将 Human Decision、Reporter、Notifier 接入统一阶段事件。

我的核心建议是：**Phase 1 不要先做目录重构，也不要先做多 Agent。先让现有 Claude Code 单 Agent 工作流变成一个可靠、可恢复、不会擅自停止的执行引擎。**

这条路线既能保留目前已有的研发成果，也能逐步把 `zentao-dev-workflow` 演进为 `devflow-ai`，避免再经历一次大规模重写。
