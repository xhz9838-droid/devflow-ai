# 核心引擎可靠性加固与真实 Agent 验证

## 一、任务目标

## 二、最高优先级原则

### 2.1 保护现有 P0 成果

项目目录：

`D:\WorkSpace\devflow-ai`

首先检查实际仓库状态，不要假设目录、分支、Git Remote 或工作区状态。

禁止：

- 删除或覆盖现有 P0 实现。

- 覆盖用户已有的未提交修改。

现有 P0 代码是本阶段的基线。优先通过增量方式完善。

### 2.2 Core 必须保持独立

Workflow Engine Core 不依赖：

- ZenTao
- DingTalk
- Jenkins
- GitHub
- Jira
- 其他项目管理、通知、CI/CD 系统

- DAG 调度
- Agent 执行
- 状态持久化
- 完成判定
- WCP
- Recovery
- HITL
- Agent 进程可靠性

禁止把项目管理系统的任务完成、关闭、删除等业务规则引入 Core。

### 2.3 SQLite 是唯一权威状态

所有 Workflow、Node、Agent Run、Decision、Checkpoint 和 Engine 运行锁状态必须保持一致。

禁止建立第二套权威状态：

- 不允许 JSON 与 SQLite 分别维护执行状态。
- JSON 可以作为导出、日志或调试产物，但不能成为状态真相来源。
- 恢复必须以 SQLite 持久化状态为准。

### 2.4 不允许虚假验收

- 必须执行真实测试。
- 必须提供测试命令和真实输出。
- 不得将代码审查结果描述为测试通过。
- 不得将 ScriptedAdapter 测试描述为真实 Claude CLI 验证。
- 外部环境不具备执行条件时，明确记录阻塞原因，不得伪造结果。
- 不允许因为测试失败就删除或弱化原有测试。

7. 验证真实 Agent Run 状态变化。
8. 验证 Completion Verifier 是否能够依据实际交付物判断节点完成。
9. 验证异常退出和超时场景。

### 真实测试任务

创建独立临时测试目录和临时 Git 仓库。

让 Claude Code 执行一个非常简单、无外部副作用的任务：

- 创建指定文件。
- 写入指定内容。
- 检查文件是否存在。
- 验证内容。
- 返回执行结果。

要求：

- 不操作真实业务项目。

- 不执行部署。
- 设置合理超时。
- 保留真实执行日志。

### 注意事项

如果 Claude CLI 需要交互式授权或登录，先检查现有可用认证状态，不要修改用户现有认证配置。

Windows 进程调用差异只能封装在 Adapter 层，不能污染 Core。

### 验收标准

必须证明：

`Workflow → Scheduler → Execution Manager → ClaudeCodeAdapter → Claude CLI → Agent Result → Verifier → Node Completed`

## DF-013：Agent 进程生命周期管理

### 目标

解决真实 Agent 长任务执行过程中的进程监控、超时、取消、异常退出和孤儿进程问题。

### 实施内容

在现有 Agent Adapter 和 Execution Manager 基础上增量完善。

1. 进程启动信息持久化：
   - PID
   - 启动时间
   - Agent Run ID
   - 工作目录
   - 进程标识
   - 超时配置

2. 进程监控：
   - 进程是否存活
   - 是否正常退出
   - 是否异常退出
   - 是否超时

3. 进程终止：
   - 支持优雅终止。
   - 超时后支持强制终止。
   - 正确处理子进程。
   - Windows 和 macOS/Linux 平台差异封装在 Adapter 内。

4. 主控重启后的进程核查：
   - 检查数据库记录的 Agent Run。
   - 判断原进程是否仍然存活。
   - 判断进程是否已退出但状态尚未更新。
   - 识别孤儿进程。
   - 防止同一节点被重复启动。

5. 执行结果收敛：
   - Agent 退出后统一更新 Agent Run。
   - 根据实际执行结果进入后续 Verifier。
   - 不允许仅凭退出码认定节点成功。

### 特别关注

PID 可能被操作系统复用，不能只凭 PID 判断进程身份。

应结合进程启动时间或平台支持的其他进程身份信息核实。

禁止使用简单的 `kill(pid)` 代替完整的进程生命周期管理。

### 验收标准

至少验证：

- 正常执行。
- 正常退出。
- 异常退出。
- 超时终止。
- 主控重启后识别原 Agent 进程。
- 孤儿进程检测。
- 子进程终止。
- 重复终止不产生非法状态转换。

## DF-014：单 Engine 实例运行保护

### 目标

默认情况下，同一个 SQLite 数据库只能有一个活动 Engine 主控执行调度。

当前阶段不实现多主控集群和 Leader Election。

### 实施内容

1. 设计数据库级 Engine 运行锁或租约。
2. Engine 启动时申请运行权。
3. 已存在有效运行权时，拒绝第二个 Engine 执行调度。
4. 运行权必须能够识别持有者。
5. 支持心跳或租约过期判断。
6. Engine 正常退出时释放运行权。
7. Engine 异常退出后允许安全恢复。
8. 防止两个 Engine 并发判断锁过期后同时取得运行权。
9. 明确只读 CLI 查询是否允许在 Engine 活动期间执行。

### 设计约束

- 使用 SQLite 事务保证竞争安全。
- 不依赖容易残留的简单 lock 文件。
- 不能通过定时删除锁记录解决并发问题。
- 不引入 Redis 等额外依赖。
- 不影响现有单 Engine 调度模型。

### 验收标准

使用两个独立进程连接同一个 DB：

- 第一个 Engine 成功获得运行权。
- 第二个 Engine 无法同时获得运行权。
- 第一个 Engine 正常退出后，第二个可以启动。
- 第一个 Engine 异常退出后，可以经过安全判定恢复。
- 不产生两个活动调度主控。

## DF-015：WCP 真实上下文续跑验证

### 目标

验证 Workflow Continuation Protocol 能够在真实 Claude Code 长任务中恢复上下文，而不只是保存数据库记录。

### 实施内容

1. 创建一个包含多个步骤的真实 Claude Code Workflow。
2. 执行前半部分任务。
3. 在适当时机触发 Checkpoint。
4. 结束当前 Agent Run。
5. 创建新的 Agent Run。
6. 从 SQLite 中读取 Continuation Context。
7. 根据结构化上下文恢复任务。
8. 继续执行未完成工作。
9. 最终由 Verifier 判断整个 Workflow 是否完成。

### Continuation Context 至少包含

- Workflow 目标
- 当前 Stage / Node
- 已完成节点及结果
- 正在执行或中断的节点
- 待执行节点
- 节点依赖关系
- 已确定的技术决策
- 已生成的交付物
- 未解决的问题
- 当前执行进度
- 下一步任务
- 最近重要事件
- 副作用执行凭证或幂等键

### 重点验证

不能简单地将旧 Prompt 全量复制给新 Agent。

新 Agent 必须能够根据结构化 Continuation Context 理解：

- 已经完成了什么。
- 哪些内容不能重复执行。
- 当前还需要完成什么。
- 为什么之前做出了某个技术决策。
- 如何继续原来的 Workflow。

### 验收标准

- 至少经历两次不同 Agent Run。
- 第二次 Agent Run 能够正确恢复上下文。
- 已完成节点不被无条件重跑。
- 已完成的副作用不重复执行。
- 最终 Workflow 正常完成。
- 完整保留 Checkpoint 和 Agent Run 历史。

## DF-016：HITL 运行中动态人工决策

### 目标

让 Agent 在执行过程中能够主动请求人工决策，而不局限于 Workflow 创建时预先定义 Decision。

### 实施内容

1. 提供 Agent 可调用的受控人工决策请求接口。
2. Agent 提交：
   - 决策标题
   - 决策原因
   - 背景信息
   - 可选方案
   - 推荐方案
   - 默认风险说明
3. Core 持久化 Decision。
4. 当前 Agent Run 安全暂停或结束当前执行段。
5. Workflow 进入 WAITING_HUMAN 或相应等待状态。
6. 不依赖通知系统实现决策本身。
7. 决策通过 CLI 或 Core 接口完成。
8. 决策结果持久化。
9. 创建新的 Agent Run 或恢复原节点执行。
10. 继续原 Workflow，而不是重新创建 Workflow。

### 并行要求

一个节点等待人工决策时：

- 不阻塞无依赖关系的其他 READY 节点。
- 依赖该节点的后续节点保持 BLOCKED。
- Decision 完成后重新计算 DAG。
- 不能因为某个节点 WAITING_HUMAN 就将整个调度器永久阻塞。

### 状态要求

- 通知成功不等于 Decision 完成。
- Decision 未被有效解决时不能继续执行依赖节点。
- 决策选项必须经过校验。
- 重复提交决策不能产生重复恢复。
- Workflow 终态必须正确清理无效 Decision。

### 验收标准

真实验证：

`Agent 执行 → 请求人工决策 → WAITING_HUMAN → 用户解决 Decision → 新 Agent Run → 恢复执行 → Verifier → Workflow Completed`

# 四、整体实施策略

## 4.1 按依赖关系推进

必须按以下顺序：

`DF-011 → DF-012 → DF-013 → DF-014 → DF-015 → DF-016 → DF-017`

其中：

- DF-011 是基线保护。
- DF-012 是真实 Agent 最小链路验证。
- DF-013 是真实 Agent 长任务的安全基础。
- DF-014 解决主控竞争。
- DF-015 验证真实上下文续跑。
- DF-016 完善运行中 HITL。
- DF-017 做综合故障验证。

不要同时大规模修改所有模块。

DF-012 可以先做受限的真实 Agent Smoke Test，但不能将这个简单测试视为真实长任务可靠性验收。DF-013 完成之前，不应进行无约束的长任务中断和恢复测试。

## 4.2 每个阶段必须形成交付物

每个 DF 任务完成后：

1. 检查实际代码修改。
2. 运行相关测试。
3. 运行必要的完整测试。
4. 更新对应实施文档。
5. 记录已知限制。
6. 记录真实验收结果。
7. 确认没有破坏此前完成的功能。
8. 再进入下一阶段。

建议文档：

- `docs/implementation/DF-011-REPORT.md`
- `docs/implementation/DF-012-REPORT.md`
- `docs/implementation/DF-013-REPORT.md`
- `docs/implementation/DF-014-REPORT.md`
- `docs/implementation/DF-015-REPORT.md`
- `docs/implementation/DF-016-REPORT.md`
- `docs/implementation/DF-017-REPORT.md`

根据现有文档目录结构适当调整，不要为了命名重复创建文档。

## 4.3 允许并行，但不能破坏依赖

可以将相互独立的测试设计、文档审查工作并行化。

涉及 SQLite Schema、状态机、Execution Manager、Recovery 的核心修改必须明确接口和依赖，避免多个 Agent 同时修改相同文件造成冲突。

不要为了多 Agent 并行而强行拆分任务。

## 4.4 执行过程中不要频繁等待用户确认

对于可以自行判断的低风险技术选择，直接采用简单、可靠的方案并记录原因。

遇到非阻塞问题：

- 记录问题。
- 选择安全的替代方案。
- 继续推进其他工作。

只有涉及不可逆操作、真实外部副作用、真实部署、用户数据破坏或必须由用户提供的凭据时，才请求人工决策。

如果当前环境没有真实 Claude CLI 或无法授权，则完成不依赖真实环境的工作，并明确报告阻塞，不得伪造真实执行结果。

# 六、P0.5 最终验收标准

只有满足以下条件，才能宣布 P0.5 完成：

1. P0 已建立 Git 基线。
2. 本机真实 Claude CLI 能通过 Adapter 执行任务。
3. Agent 进程可以监控、超时、取消和终止。
4. Engine 重启后能够识别并处理原 Agent 进程。
5. 同一个 DB 不会被两个活动 Engine 同时调度。
6. WCP 能够支持真实 Agent Run 之间的上下文续跑。
7. 已完成节点不会被无条件重复执行。
8. Agent 能在执行过程中请求人工决策。
9. 人工决策后能够继续原 Workflow。
10. Engine 强制退出后能够恢复 Workflow。
11. 关键故障场景有自动化测试。
12. 原有 P0 测试全部保持通过。
13. 完整 P0.5 验收报告真实反映测试结果。

最终必须完成一次完整的真实 E2E：

**创建 Workflow → 多节点 DAG 调度 → 真实 Claude Code 执行 → Checkpoint → Agent Run 交接 → Engine 中断 → Engine 重启 → Recovery → 人工决策 → 继续执行 → Verifier → Workflow Completed。**

最终输出：

`docs/implementation/P0.5-ACCEPTANCE-REPORT.md`

报告必须包含：

- P0.5 实施内容
- 架构变化
- 数据库变化
- Git 提交记录
