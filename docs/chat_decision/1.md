# **二、P0.5：核心引擎可靠性加固**

这是我建议下一步立即启动的阶段。

P0 的架构和主要功能不要推倒重来，而是在现有实现上补齐真实运行环境中的可靠性。

## **P0.5-1：真实 Claude Code Adapter 验证**

最高优先级

目前 E2E 使用的是 ScriptedAdapter，尚未验证真实 Claude CLI。

需要验证：

1. 从 DevFlow AI 启动真实 Claude CLI。
2. 正确传递工作目录、Prompt 和执行配置。
3. 实际获取 stdout、stderr 和退出码。
4. 长任务持续运行时心跳正常。
5. Agent 执行结果正确返回 Core。
6. Verifier 根据真实执行结果进行验收。
7. 真实 Agent 执行失败时能够触发 Retry。
8. 真实 Agent 执行过程中断后能够恢复。

特别注意 Windows 环境：

- `claude` 可能解析为 `.cmd` 文件。
- 当前 `shell=False` 的实现需要验证。
- 不应为了兼容 `.cmd` 就直接在 Core 中引入 Shell 命令拼接。
- 应由 ClaudeCodeAdapter 自己处理平台差异。

**验收标准：** 不使用 ScriptedAdapter，真实 Claude CLI 完成一个简单研发任务，并通过 Core 的完成判定。

建议先用临时 Git 仓库和无副作用的小任务测试，避免直接在正式项目中做首次验证。

## **P0.5-2：Agent 进程生命周期管理**

最高优先级

这是当前最需要补齐的工程能力。

目前已知：

- `cancel` 只是状态级操作。
- 外部进程不主动 kill。
- 硬崩溃时可能留下孤儿 Agent。
- 孤儿 Agent 可能继续修改工作目录。

建议实现：

| 能力   | 具体要求                             |
| ---- | -------------------------------- |
| 进程标识 | Agent Run 持久化 PID、启动时间、进程信息      |
| 进程监控 | 检查进程是否存活                         |
| 超时控制 | 超时后终止进程                          |
| 主动取消 | 支持优雅终止和强制终止                      |
| 进程树  | 尽可能管理 Agent 子进程                  |
| 重启恢复 | 重新启动后核实原 Agent 是否仍在运行            |
| 结果收敛 | 进程终止后重新核对 Run、Node 和 Workflow 状态 |

建议将 Agent Adapter 从简单的同步执行接口逐步增强为可监督的执行会话接口。

不要让 Core 直接管理 Windows 或 macOS 的进程 API，操作系统差异仍然封装在 Adapter 内。

## **P0.5-3：单 Engine 运行保护**

目前 ADR 明确采用单主控模型，没有 Leader Election。

P0-ARCHITECTURE_ADR-001-P0-CORE_P0-REPORT.txt



这不一定需要立即实现分布式协调，但必须明确并落实单实例边界。

建议：

- 同一个数据库默认只允许一个活动 Engine 主控。
- Engine 启动时获得数据库级运行锁或实例租约。
- 非活动实例不能调度节点。
- CLI 的只读查询可以考虑独立允许。
- Engine 崩溃后允许恢复锁。
- 不能仅依靠进程启动时创建一个容易残留的 lock 文件。

暂时不做多主控、分布式调度和 Leader Election 集群。

## **P0.5-4：WCP 真实上下文续跑验证**

目前 WCP 已具备 Checkpoint 和 Continuation Context，但还需要证明真实 Agent 能够使用它继续工作。

需要验证：

- Claude Code 上下文即将达到限制时，如何触发交接。
- 新 Agent Run 能否从 Continuation Context 重建任务。
- 是否能够恢复之前的技术决策。
- 是否能准确识别已经完成的工作。
- 是否会重复执行已有副作用。
- 是否能够继续完成原始 Workflow。

重点不是保存完整对话，而是验证结构化上下文能否支持真实研发任务连续执行。

## **P0.5-5：HITL 动态决策能力**

目前 HITL 主要支持节点执行前的人工决策。

后续真实研发过程中，还会遇到：

- Agent 执行中发现需求不明确。
- 发现高风险技术选择。
- 需要人工选择实现方案。
- 发现外部环境不满足继续条件。
- 需要人工决定是否继续下一步。

建议增加运行中人工决策的机制。

关键要求：

- Agent 可以通过受控接口请求人工决策。
- 当前 Agent Run 可以安全暂停或结束当前执行段。
- Workflow 和 Decision 状态持久化。
- 其他独立 DAG 节点继续执行。
- 决策完成后重建上下文。
- 从原节点继续，而不是重新启动整个 Workflow。

这项能力可以列入 P0.5 后半段，不必阻塞真实 Claude CLI 的首次验证。

## **P0.5-6：可靠性专项测试**

建议增加以下测试场景：

| 测试场景            | 验收要求          |
| --------------- | ------------- |
| 主控进程强制退出        | 重启后能够恢复       |
| Agent 进程残留      | 能检测并处理        |
| Agent 超时        | 能正确终止并记录      |
| 重复恢复            | 不重复调度         |
| 并发启动            | 不产生两个活动主控     |
| Checkpoint 写入失败 | 不伪造成功         |
| 人工决策后重启         | 能恢复原 Workflow |
| Agent 已完成但状态未推进 | 复核结果而非盲目重跑    |
| 工作目录发生外部修改      | 能识别并按策略处理     |

**P0.5 完成标准：真实 Claude CLI + 真实中断 + 主控重启 + 恢复续跑 + 人工决策 + 最终完成。**

# **三、P1：建立真正可插拔的 Agent 和 Provider 体系**

P0.5 通过后，开始 P1。

这里有一个架构重点：**Agent Adapter 和 Provider 是两种完全不同的插件。**

- Agent Adapter 负责执行任务。
- Provider 负责向外部系统提供能力。
- Workflow Core 负责整个流程的编排和状态管理。

不要把两者混成一个 Plugin 接口。

## **P1-1：Agent Adapter 标准化**

P1 · 第一项

先完善已有的 `AgentAdapter`，再增加其他 Agent。

建议统一以下能力：

| 能力           | 说明                 |
| ------------ | ------------------ |
| execute      | 执行任务               |
| start        | 启动执行会话             |
| poll         | 查询执行状态             |
| terminate    | 终止执行               |
| get_result   | 获取执行结果             |
| resume       | 恢复已有会话             |
| capabilities | 声明当前 Adapter 支持的能力 |

注意：并不是每个 Agent 都支持所有能力。

建议 Adapter 返回能力声明，Core 根据能力选择执行策略，而不是假设 Codex、Claude Code、OpenCode 的运行机制完全相同。

实施顺序：

1. 完善 ClaudeCodeAdapter。
2. 定义能力声明和统一执行会话。
3. 增加 CodexAdapter。
4. 增加 OpenCodeAdapter。
5. 验证同一个 Workflow 可以切换不同 Agent。

不要求 P1 一开始就同时支持多个 Agent。先让统一接口在 Claude Code 上经过真实验证。

## **P1-2：Notification Provider**

P1 · HITL 外部通知

通知系统是 HITL 的外部交互通道，不是决策引擎本身。

建议先接入钉钉，后续再扩展其他通知平台。

支持事件：

- Workflow 开始、完成、失败。
- Agent 执行异常。
- Workflow 中断。
- 人工决策请求。
- 人工决策结果。
- 恢复执行。
- 重试和最终失败。

必须具备：

- 通知事件持久化。
- 可靠投递和失败重试。
- 通知状态追踪。
- 决策回调。
- 用户回复与 Decision 关联。
- 通知失败不改变 Workflow 状态。

这里建议增加通知投递记录，但不要让通知 Provider 直接修改 Core 的 Workflow 状态。

## **P1-3：Project Management Provider**

P1 · 项目管理插件

这是用户输入研发任务的一种来源，不是 Workflow 的必要条件。

先定义统一接口：

```
class ProjectManagementProvider:    def get_task(self, task_id): ...    def update_progress(self, task_id, progress): ...    def report_result(self, task_id, result): ...
```

然后接入 ZenTao。

需要支持：

- 获取需求和任务信息。
- 将外部任务转换成 Workflow 输入。
- 同步阶段进度。
- 回写执行报告。
- 处理回写失败和补偿。

以后可以接入 Jira、GitHub Issues 等。

特别注意：

**不能让 Core 依赖 ZenTao 的任务状态，也不能要求每个 Workflow 都绑定项目管理任务。**

## **P1-4：Git Provider**

支持统一管理：

- Git 仓库。
- 分支。
- 工作区。
- Commit。
- Diff。
- 文件变更。
- Worktree。

其中 Worktree 值得重点考虑。

因为未来多 Agent 并行执行时，不同 Agent 如果共享一个工作目录，容易产生代码覆盖和文件冲突。

建议先实现 Git 基础能力，等多 Agent 并行开发真正需要时，再增加 Worktree 隔离策略。

## **P1-5：CI/CD Provider**

支持：

- Jenkins。
- GitHub Actions。
- GitLab CI。
- 其他 CI 平台。

CI/CD 只负责构建、测试、部署等外部执行。

Core 负责：

- 发起请求。
- 保存执行记录。
- 等待结果。
- 处理成功、失败和超时。
- 通过 HITL 管理需要人工批准的部署决策。

真实部署不能因为工作流自动化而绕过人工确认。

## **P1-6：Provider 注册与配置**

统一管理 Provider：

- Provider ID。
- Provider 类型。
- 配置入口。
- 能力声明。
- 初始化。
- 健康检查。
- 生命周期。
- 错误处理。

第一版只需要本地 Python 插件注册，不需要插件市场、远程插件下载和复杂依赖管理。

# **四、P1.5：从工作流引擎升级为研发自动化引擎**

核心执行和插件体系稳定后，再增加研发领域的高级能力。

| 子任务    | 能力                        | 价值             |
| ------ | ------------------------- | -------------- |
| P1.5-1 | Workflow Template         | 预定义研发流程        |
| P1.5-2 | Task Decomposition        | 自动拆分复杂研发任务     |
| P1.5-3 | Dynamic DAG               | 执行期间根据结果动态调整计划 |
| P1.5-4 | Multi-Agent Collaboration | 多 Agent 协作     |
| P1.5-5 | Workspace Isolation       | 多 Agent 工作区隔离  |
| P1.5-6 | Quality Gates             | 统一代码质量和测试门禁    |

这里我认为最值得投入的是三个能力：

**1. 自动任务拆解**

用户只提交一个复杂研发目标，Workflow 自动生成分析、设计、开发、测试、验收等 DAG 节点。

**2. 动态 DAG**

实际开发过程中可能发现原计划不够完整，允许在受控条件下新增节点、调整依赖、重新规划后续执行。

**3. 多 Agent 协作**

例如：

- Agent A：需求分析。
- Agent B：后端开发。
- Agent C：前端开发。
- Agent D：测试。
- Agent E：代码审查。

由 Core 控制调度、依赖和完成判定，而不是让一个 Agent 自己管理所有子 Agent。

但多 Agent 不应只是并发启动多个 CLI 进程，还需要工作区隔离、资源控制、结果合并和冲突处理。
