# 核心引擎骨架搭建与分阶段实施

## 一、项目背景

项目名称：DevFlow AI

项目目录：

`D:\WorkSpace\devflow-ai`

这是一个独立的 Git 仓库，已经完成旧版仓库和代码来源盘点。

相关文档：

需要从产品目标出发，建立 DevFlow AI 自己的核心架构。

## 二、产品定位

DevFlow AI 是一个面向 AI Coding Agent 的轻量级研发工作流引擎。

它负责：

- 管理完整工作流生命周期。
- 将复杂研发任务拆解为 DAG。
- 调度和管理 AI Coding Agent。
- 持久化工作流执行状态。
- 判断任务是否真正完成。
- 管理长任务上下文和 Continuation。
- 检测执行中断并恢复。
- 管理人工决策和等待状态。
- 处理失败、重试、超时和恢复。

项目管理系统、通知系统、Git、CI/CD 均为可插拔集成。

**核心原则：没有任何外部 Provider，DevFlow AI 也必须能够独立创建、执行、恢复和完成一个 Workflow。**

## 三、架构原则

### 1. Workflow Core 独立

核心引擎不能依赖：

- 禅道或其他项目管理系统。
- 钉钉、企业微信等通知平台。
- Jenkins 等 CI/CD 平台。
- Claude Code 的全局 Skill 安装目录。
- 某个特定 Agent 的私有接口。

### 2. Agent 可插拔

通过 Agent Adapter 统一管理不同 Agent。

初期优先支持 Claude Code，但核心接口不能直接绑定 Claude Code 的具体实现。

后续再接入 Codex、OpenCode 等 Agent。

### 3. Provider 可插拔

项目管理、通知、Git、CI/CD 分别定义独立 Provider 接口。

没有配置 Provider 时，核心工作流仍然可以正常执行。

Provider 失败不能破坏核心 Workflow 状态的一致性。

### 4. 状态持久化

SQLite 是唯一权威状态来源。

所有重要生命周期变化、节点执行、人工决策、检查点和恢复记录都必须持久化。

不能同时维护 SQLite 和 JSON 文件作为两套权威状态。

### 5. 先最小闭环，再扩展

不要一开始建立重量级平台。

不引入微服务、Kubernetes、Kafka、RabbitMQ 等非必要基础设施。

优先复用旧版经过验证的状态管理、Agent 执行、Verifier、Retry、Recovery 和 HITL 能力，但必须先检查其边界是否适合新架构。

# 四、P0：Workflow Engine 核心能力

P0 是第一优先级，必须先建立。

## P0-1：项目骨架和核心架构

建立清晰的代码分层：

- Workflow Core
- Agent Adapter
- Provider Layer
- Persistence
- Control Interface

先定义模块职责和依赖方向。

要求：

- Core 不依赖具体 Adapter 和 Provider。
- Adapter、Provider 通过接口接入 Core。
- 状态持久化独立于业务逻辑。
- 各模块可以独立测试。
- 统一配置、日志、异常和运行环境管理。

先形成实际可用的项目结构，不要为了未来可能出现的需求创建大量空目录和空类。

交付：
- 项目目录结构。
- 核心模块说明。
- 模块依赖关系。
- 最小可运行入口。

## P0-2：Workflow Lifecycle

建立统一工作流生命周期和状态机。

至少支持：

- CREATED
- INITIALIZING
- RUNNING
- WAITING
- WAITING_HUMAN
- RECOVERING
- COMPLETED
- FAILED
- CANCELLED

根据实际需要区分暂停、超时等状态，但不要无意义地增加状态。

必须明确：

- 合法状态转换。
- 状态转换触发条件。
- 状态转换记录。
- 状态持久化。
- 非法状态转换处理。
- 终态判定。

Workflow 状态与 DAG Node 状态分开管理。

不能通过 Agent 进程退出码直接决定 Workflow COMPLETED。

交付：
- Workflow 模型。
- 生命周期状态机。
- 状态转换服务。
- 状态机测试。

## P0-3：SQLite State Management

建立统一持久化模型。

至少覆盖：

- workflows
- workflow_stages
- workflow_nodes
- agent_runs
- execution_events
- checkpoints
- human_decisions
- retry_records

根据实际设计增加必要字段和索引。

要求：

- 支持 Schema 版本管理和迁移。
- 关键状态更新具备事务一致性。
- 记录状态变化时间和原因。
- 支持查询 Workflow 完整执行历史。
- 支持从持久化状态恢复运行。
- 避免重复执行和重复写入。
- 不能出现两套权威状态。

SQLite 作为第一阶段默认存储，不提前抽象复杂数据库集群。

交付：
- 数据模型。
- DDL 和迁移机制。
- Repository / State Manager。
- 持久化测试。

## P0-4：DAG Scheduler

建立独立 DAG 调度引擎。

这是 DevFlow AI 的核心模块之一。

支持：

- 创建 DAG。
- 定义节点和依赖。
- 检查循环依赖。
- 拓扑排序。
- 判断节点是否满足执行条件。
- 调度独立节点。
- 并行执行符合条件的节点。
- 节点失败处理。
- 节点阻塞传播。
- 节点重试。
- DAG 整体完成判定。

节点至少具备：

- node_id
- workflow_id
- name
- status
- dependencies
- execution_config
- retry_policy
- input
- output
- error
- timestamps

节点状态至少考虑：

- PENDING
- READY
- RUNNING
- WAITING_HUMAN
- BLOCKED
- SUCCEEDED
- FAILED
- SKIPPED
- CANCELLED

要求：

- 独立节点可以并行执行。
- 有依赖的节点必须等待前置节点成功。
- 人工等待节点不能阻塞无依赖关系的独立节点。
- 失败节点应根据策略重试或阻塞下游节点。
- 调度器必须能够从数据库状态重新计算可执行节点。
- 避免同一个节点被重复调度。

不要把 DAG 调度逻辑写进 Skill 或 CLI。

交付：
- DAG 模型。
- Scheduler。
- 节点状态管理。
- 并发控制。
- DAG 测试。

## P0-5：Agent Execution Manager

建立统一 Agent 执行管理层。

负责：

- 创建 Agent Run。
- 启动 Agent。
- 管理运行状态。
- 记录执行输出和事件。
- 处理超时。
- 检测异常退出。
- 管理执行上下文。
- 将结果反馈给 DAG Scheduler。

通过 Agent Adapter 接口执行具体 Agent。

第一阶段只需要让 Claude Code Adapter 能够完成实际调用。

但不要让 Scheduler 直接执行 Claude Code 命令。

需要区分：

- Workflow
- DAG Node
- Agent Run

三者生命周期不能混为一谈。

交付：
- Agent Adapter 接口。
- Agent Execution Manager。
- 最小 Claude Code Adapter。
- 执行状态持久化。
- 执行测试。

## P0-6：Completion Verifier

建立独立完成判定模块。

核心原则：

**Agent 执行结束，不代表任务完成。**

Verifier 应根据节点和 Workflow 的验收条件进行判断。

支持：

- 检查执行结果。
- 检查必需交付物。
- 检查测试结果。
- 检查节点验收条件。
- 记录验证证据。
- 判断通过或不通过。
- 返回失败原因。
- 决定是否允许进入下一阶段。

定义统一 VerifyReport。

至少包含：

- passed
- summary
- evidence
- failed_conditions
- verified_at

Workflow 完成条件必须由 Core 统一判定。

只有所有必需节点完成、验收通过、没有未解决阻塞事项时，Workflow 才能进入 COMPLETED。

不能将第三方项目管理系统的任务状态作为 Workflow 完成的必要条件。

交付：
- Verifier 接口。
- 完成判定服务。
- VerifyReport。
- 完成判定测试。

## P0-7：Workflow Continuation Protocol

这是长任务可靠运行的关键能力，必须作为核心协议设计，而不是简单保存一段 Agent 对话文本。

建立统一的 Workflow Continuation Protocol（WCP）。

目标：

无论 Agent 正常结束、上下文接近上限、执行中断、进程崩溃还是需要人工决策，都能够基于持久化状态恢复原 Workflow。

WCP 至少包含：

### A. Checkpoint

记录：

- workflow_id
- 当前阶段
- 当前节点
- 已完成节点
- 执行中节点
- 待执行节点
- 依赖关系
- 当前执行结果
- 重要上下文摘要
- 已产生的交付物
- 未解决问题
- 下一步执行计划
- 最近一次状态事件

### B. Continuation Context

建立标准化上下文交接结构。

Agent 不应依赖完整历史对话才能继续执行。

必须能够从检查点恢复：

- 当前任务目标。
- 已经完成的工作。
- 当前工作进度。
- 关键技术决策。
- 未完成事项。
- 下一步操作。
- 不能重复执行的副作用操作。

### C. Continuation 流程

支持：

1. 主动保存检查点。
2. 阶段完成自动保存。
3. Agent 上下文不足时交接。
4. Agent 异常退出后恢复。
5. 人工决策完成后恢复。
6. 从检查点重新构建执行上下文。

### D. 一致性要求

- Checkpoint 必须与 SQLite 状态保持一致。
- 不允许检查点记录的节点状态与数据库权威状态冲突。
- 恢复前必须检查当前 Workflow 和 Node 状态。
- 已成功完成的节点不能无条件重新执行。
- 对存在外部副作用的操作，需要有幂等键或执行凭证。
- 检查点保存失败时不能假装保存成功。

交付：
- WCP 数据结构和协议文档。
- Checkpoint Manager。
- Continuation Context Builder。
- 保存、恢复和重建上下文能力。
- 相关测试。

## P0-8：Recovery Engine

建立统一中断恢复机制。

支持识别：

- Agent 正常退出。
- Agent 异常退出。
- Agent 进程意外消失。
- 执行超时。
- 主控进程异常退出。
- 主机重启后的未完成任务。
- Checkpoint 不完整。
- 节点状态与 Agent Run 状态不一致。

恢复流程：

1. 读取 SQLite 权威状态。
2. 识别未完成 Workflow。
3. 检查 Agent Run 和节点状态。
4. 判断是否可以继续、重试、等待或失败。
5. 检查已有执行凭证和副作用。
6. 重建 Continuation Context。
7. 恢复 DAG 调度。
8. 记录恢复事件。

要求：

- 区分 FAILED、INTERRUPTED、RECOVERING。
- 不能把中断直接判定为任务失败。
- 不能盲目重新执行已成功节点。
- 支持最大重试次数和退避策略。
- 支持恢复失败后的人工处理。
- 恢复操作具备幂等性。

交付：
- Recovery Manager。
- Retry Policy。
- 启动时恢复检查。
- 中断恢复测试。

## P0-9：HITL Human Decision Engine

人工决策是 Workflow Core 的原生能力。

不要把 HITL 仅仅实现为钉钉消息或聊天窗口。

建立独立决策模型：

- decision_id
- workflow_id
- node_id
- decision_type
- question
- context
- options
- status
- selected_option
- decision_payload
- created_at
- resolved_at

支持：

- 创建人工决策。
- WAITING_HUMAN 状态持久化。
- 人工选择或输入决策。
- 决策结果校验。
- 决策结果持久化。
- 决策超时。
- 决策取消。
- 决策后恢复原 Workflow。

核心要求：

1. 人工决策不能丢失。
2. 通知成功不代表人工决策完成。
3. 没有有效决策不能自动放行。
4. WAITING_HUMAN 节点不应阻塞 DAG 中无依赖关系的其他节点。
5. 决策完成后可以从原检查点恢复。
6. 不要求用户重新启动整个工作流。
7. 决策结果需要完整审计记录。

第一阶段允许通过 CLI 或本地接口完成决策，不要求立即接入钉钉。

交付：
- Human Decision Manager。
- Decision State Machine。
- Decision Store。
- 决策恢复流程。
- HITL 测试。

## P0-10：Core 端到端闭环

将 P0-1 至 P0-9 组合起来，建立最小可运行 Workflow。

必须演示：

1. 创建 Workflow。
2. 初始化工作流。
3. 创建 DAG。
4. 调度多个节点。
5. Agent 执行节点。
6. 保存执行结果。
7. Verifier 验收。
8. 创建 Checkpoint。
9. 模拟 Agent 中断。
10. Recovery 恢复执行。
11. 节点进入 WAITING_HUMAN。
12. 完成人工决策。
13. 恢复原 Workflow。
14. 所有节点验收通过。
15. Workflow 进入 COMPLETED。

验收时必须证明：

- 不依赖禅道。
- 不依赖钉钉。
- 不依赖 Jenkins。
- 不依赖外部项目管理系统。
- SQLite 状态能够独立支撑完整执行和恢复。

P0 完成后，DevFlow AI 必须成为一个能够独立运行的工作流引擎，而不是一组互不关联的模块。

# 五、P1：Agent 与 Provider 扩展

P0 完成并通过端到端测试后，再进入 P1。

## P1-1：Agent Adapter 扩展

在 Claude Code Adapter 基础上完善统一接口。

逐步接入：

- Codex Adapter
- OpenCode Adapter

每个 Adapter 声明 capabilities，例如：

- 支持启动执行。
- 支持恢复会话。
- 支持获取执行状态。
- 支持终止执行。
- 支持结构化输出。
- 支持工具调用。

不能假设不同 Agent 具有相同的执行和恢复能力。

## P1-2：Provider 接口体系

按领域建立独立接口：

- ProjectManagementProvider
- NotificationProvider
- GitProvider
- CIProvider

没有 Provider 时，Core 必须正常工作。

Provider 不得直接修改 Workflow 核心状态。

外部调用结果由 Core 统一记录和处理。

## P1-3：CLI 控制入口

建立统一 CLI：

- workflow create
- workflow start
- workflow status
- workflow inspect
- workflow resume
- workflow cancel
- workflow decisions
- workflow events

具体命令结构可以根据当前项目技术栈调整。

CLI 仅作为 Core 的控制入口，不包含核心业务状态机和 DAG 调度实现。

## P1-4：通知 Provider

通过 NotificationProvider 支持：

- 工作流开始。
- 阶段完成。
- Agent 异常。
- Workflow 中断。
- 人工决策请求。
- 决策完成。
- 恢复执行。
- 最终完成或失败。

第一阶段可以接入钉钉。

通知失败不能改变 Workflow 的真实执行状态。

## P1-5：Project Management Provider

接入禅道等项目管理系统。

外部项目管理系统负责：

- 需求和任务来源。
- 任务信息读取。
- 任务进度同步。
- 执行结果回写。

项目管理系统不是 Workflow Engine 的运行前提。

Workflow 可以由 CLI 直接创建，也可以由其他 Provider 创建。

任何 Provider 的缺失都不能导致核心引擎无法执行。

## P1-6：Git / CI Provider

支持：

- Git 仓库信息。
- 分支和提交信息。
- 变更记录。
- CI 构建结果。
- 部署状态。

真实部署操作必须保留必要的人工授权流程。

## P1-7：Workflow Template

支持复用工作流模板。

例如：

- Bug Fix Workflow
- Feature Development Workflow
- Code Review Workflow
- Test & Verification Workflow
- Release Workflow

模板只定义工作流结构、节点和策略，不应绑定某一个 Agent 或 Provider。

## 八、代码实施要求

1. 先检查现有 DevFlow AI 仓库，不要假设它是空项目。
2. 优先复用旧版成熟代码，但按新架构重新确定模块边界。
3. 不要直接复制旧版 Skill 的完整执行流程。
4. 不要将外部项目管理系统逻辑放进 Workflow Core。
5. 不要为了未来扩展创建大量空接口和空实现。
6. 每个阶段完成后运行对应测试。
7. 每个核心模块必须有清晰的职责、输入、输出和异常处理。
8. SQLite 是唯一权威状态来源。
9. Windows 和 macOS 的路径、进程管理和 Shell 差异通过平台适配处理，不要将 Windows 专属实现写进 Core。
10. 先保证 Claude Code 单 Agent 端到端闭环，不提前追求多 Agent 并行。
