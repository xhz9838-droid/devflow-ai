# DevFlow AI — DF-018 Planning Layer & Plan / Execute 双阶段工作流实现

## 任务目标

在现有 DevFlow AI P0 / P0.5 Workflow Engine 基础上，增量实现 Planning Layer 和 Plan / Execute 双阶段工作流。

本次任务不仅是增加一个任务拆分功能，而是让 DevFlow AI 具备以下完整能力：

1. 理解用户提出的软件研发目标。
2. 在执行前调研项目代码、文档、技术规范和现有架构。
3. 识别真正影响实现方向的关键不确定性。
4. 按照 Decision Policy 判断哪些问题需要询问用户，哪些问题由 AI 自主决定。
5. 将研发目标转化为结构化 Execution Plan，包括 DAG、Agent 分工、依赖关系和验收标准。
6. 在计划确认后，将 Plan Snapshot 交给现有 Workflow Core 执行。
7. 执行过程中发现重大偏差时，通过受控的 Plan Change Request 处理，而不是擅自修改原计划。
8. 保留现有 P0 / P0.5 的调度、状态管理、WCP、Recovery、HITL 和 Verifier 能力。

最终目标：

**用户提出研发目标 → AI 调研和分析 → 必要时澄清 → 生成执行计划 → 用户确认 → 多 Agent 执行 → 测试与验收 → 失败恢复 → 最终交付。**

# 二、核心架构决策

## 2.1 采用 Planning Layer + Workflow Core

不将系统拆成两个独立的 Plan Engine 和 Execute Engine。

采用以下结构：

```text
User Input
    |
    v
Planning Layer
    |
    +-- Requirement Analysis
    |
    +-- Repository Context
    |
    +-- Technical Investigation
    |
    +-- Decision Policy
    |
    +-- Clarification Manager
    |
    +-- DAG Generator
    |
    +-- Acceptance Criteria
    |
    v
Execution Plan
    |
    v
Plan Snapshot
    |
    v
Plan Confirmation
    |
    v
Workflow Core
    |
    +-- Workflow Lifecycle
    |
    +-- DAG Scheduler
    |
    +-- Agent Execution Manager
    |
    +-- WCP
    |
    +-- Recovery / Retry
    |
    +-- HITL
    |
    +-- Verifier
    |
    v
Delivery Result
```

## 2.2 Planning Layer 的职责

Planning Layer 负责：

- 理解用户需求。
- 分析任务范围。
- 调研代码仓库。
- 阅读相关文档和现有实现。
- 分析技术方案。
- 识别风险和不确定性。
- 按 Decision Policy 处理决策。
- 生成结构化 DAG。
- 分配 Agent。
- 定义任务输入、输出和依赖。
- 定义验收标准。
- 生成 Execution Plan。

Planning Layer 不负责：

- 实际研发任务的 DAG 调度。
- Agent 执行生命周期管理。
- Agent 运行状态管理。
- Workflow 状态管理。
- Checkpoint 和 Recovery。
- 最终执行完成判定。

这些仍由现有 Workflow Core 负责。

## 2.3 Workflow Core 的职责

现有 Workflow Core 继续作为系统唯一的执行引擎。

它只接收经过校验和确认的 Execution Plan Snapshot。

执行期间：

- 不重新进行完整需求规划。
- 不擅自改变已确认的任务范围。
- 不允许 Agent 直接修改 Workflow 状态。
- 不允许 Agent 绕过 Core 创建或修改执行节点。
- 所有执行状态通过现有 Core 和 SQLite 管理。
- 所有完成判定继续使用 Verifier 证据。

# 三、Plan / Execute 双阶段工作流

## 3.1 Plan 阶段

Plan 阶段是执行前的准备阶段，允许 AI 进行调研、分析和有限的用户交互。

建议生命周期：

```text
DRAFT
  |
  v
INVESTIGATING
  |
  v
ANALYZING
  |
  +----> NEEDS_CLARIFICATION
  |               |
  |               v
  |          ANSWERED
  |               |
  +---------------+
  |
  v
PLAN_READY
  |
  v
CONFIRMED
  |
  v
EXECUTION_READY
```

具体状态可以根据现有状态管理方式调整，但必须清晰区分：

- 计划尚未完成。
- 等待用户澄清。
- 计划已生成。
- 计划已确认。
- 已交给执行引擎。

Plan 阶段需要完成：

1. 接收用户研发目标。
2. 识别项目、代码仓库和任务范围。
3. 收集必要上下文。
4. 分析相关代码和文档。
5. 识别需求缺口和技术风险。
6. 使用 Decision Policy 判断是否需要提问。
7. 生成 Execution Plan。
8. 校验 DAG、依赖关系和验收标准。
9. 展示计划摘要。
10. 等待用户确认。

Plan 阶段可以与用户交互，但不能把所有实现细节都变成问题。

## 3.2 Execute 阶段

Execute 阶段接收已确认的 Plan Snapshot。

执行流程：

```text
Confirmed Plan Snapshot
       |
       v
Create Workflow
       |
       v
Validate Plan
       |
       v
DAG Scheduler
       |
       v
Dispatch Agents
       |
       v
Execute Nodes
       |
       v
Verifier
       |
       +----> Failed / Retry / Recovery
       |
       +----> HITL Decision
       |
       +----> Plan Change Request
       |
       v
All Acceptance Criteria Passed
       |
       v
Workflow Completed
```

执行阶段必须遵循以下规则：

1. 只能执行已确认的 Plan Snapshot。
2. 不允许因 Agent 自己的偏好随意扩大任务范围。
3. 普通实现细节由 Agent 自主决定。
4. 发现低风险问题时，优先采用可逆方案继续执行。
5. 发现重大业务不确定性时，创建 HITL Decision。
6. 发现原计划存在重大错误时，创建 Plan Change Request。
7. 已完成节点不得因普通计划调整而无条件重跑。
8. 所有变更必须记录原因、影响范围和审批结果。
9. 执行过程继续使用现有 WCP、Recovery、Retry 和 Verifier。
10. 执行阶段不允许通过普通 CLI 对话临时向用户提问并中断流程。

如果配置了 HITL Provider，重大决策通过 HITL Provider 通知用户，并在用户回复后自动恢复。

如果尚未配置外部通知 Provider，保留现有 HITL 持久化和 CLI 查询、回复能力，不得让 Core 依赖钉钉。

# 四、Plan Decision Policy — 需求澄清与自主决策策略

本部分是 DF-018 的核心要求。

必须将 Decision Policy 作为 Planning Layer 的正式策略实现，而不是仅写在 Prompt 或文档中的建议。

核心原则：

**不是所有不确定性都需要询问用户。只有可能导致重大返工、业务错误、范围偏差或不可逆影响的问题，才需要用户参与。**

## 4.1 四级决策分类

### L0：明确需求

特征：

- 用户已经明确说明。
- 现有代码或文档能够确认。
- 不存在实质性歧义。

处理方式：

- 直接纳入计划。
- 不询问用户。
- 不重复确认已经明确的内容。

### L1：普通技术实现决策

特征：

- 技术实现方式存在多个选择。
- 不影响核心业务语义。
- 属于 Agent 的专业职责。
- 能够通过代码结构、项目规范或行业常规推导。

例如：

- 类名、变量名。
- 普通目录结构。
- 内部方法拆分。
- 常规异常处理。
- 单元测试组织方式。
- 不影响接口契约的内部实现选择。

处理方式：

- Agent 自主决定。
- 优先遵循现有项目规范。
- 记录选择理由。
- 不询问用户。

### L2：低风险不确定性

特征：

- 存在一定不确定性。
- 有多个可行方案。
- 选择错误不会导致严重业务问题。
- 方案可逆或修改成本较低。

处理方式：

- 优先调研代码、文档和项目规范。
- 给出推荐方案。
- 默认采用最佳方案继续规划。
- 在 Plan 中记录决策和假设。
- 不阻塞用户。
- 不为了追求百分之百确定性而反复提问。

如果存在明显风险，可以在计划摘要中提示，但不必要求用户逐项确认。

### L3：重大决策

特征：

可能造成以下问题之一：

- 核心业务逻辑理解错误。
- 需求范围发生实质性变化。
- 数据模型或数据库结构存在重大不确定性。
- 数据迁移、删除或不可逆操作。
- 对外 API 契约发生重大变化。
- 权限、安全或数据隔离策略存在重大不确定性。
- 兼容性和生产环境影响重大。
- 多个方案会导致明显不同的产品行为。
- 继续执行可能产生较大返工。
- 缺少关键业务规则，无法合理推导。

处理方式：

- 不得擅自猜测。
- 不得用 L1/L2 自主决策掩盖 L3 风险。
- 创建 Clarification Item。
- 提供必要背景和影响说明。
- 提供推荐方案及推荐理由。
- 尽可能提供少量清晰的选项。
- 等待用户回答。
- 收到回答后更新 Plan，再继续规划。

## 4.2 澄清前必须先调研

禁止在没有调查的情况下直接询问用户。

每个候选问题必须先执行：

1. 搜索相关代码。
2. 检查现有接口和数据模型。
3. 查阅相关文档。
4. 检查项目约定和历史实现。
5. 判断是否能够从上下文推导。
6. 判断是否存在低风险默认方案。

只有仍然无法解决且达到 L3 标准的问题，才进入澄清列表。

## 4.3 控制提问数量

避免过度询问。

默认原则：

- 普通研发任务：0–3 个问题。
- 存在多个重大业务歧义的复杂任务：可以批量提出 3–5 个问题。
- 不设置为了凑数量而提问的目标。
- 没有 L3 问题时，直接生成计划。
- 不将一个问题拆成多个无意义的小问题。
- 能合并的问题尽量合并。
- 已明确的信息不得重复询问。
- 用户已给出默认值或授权时，不再重复确认。

问题应尽量一次性批量提出，避免多轮零散追问。

## 4.4 每个澄清问题的格式

每个问题至少包含：

- 问题内容。
- 为什么需要确认。
- 已完成的调研。
- 不同选择的影响。
- 推荐方案。
- 用户可以直接选择的选项。

示例：

```text
问题：该接口是否需要兼容旧版调用方式？

背景：
当前项目存在两个调用入口，新的实现可能影响旧调用方。

选项：
A. 保持兼容，新增字段采用可选方式。
B. 直接调整接口契约，同步修改所有调用方。

推荐：A

原因：
当前需求没有明确要求废弃旧接口，保持兼容可以降低影响范围。
```

不要把技术实现细节伪装成业务问题交给用户。

## 4.5 用户授权与默认决策

支持用户在任务输入中明确授权：

- 可以自主选择技术方案。
- 可以采用项目现有规范。
- 可以在低风险情况下自行确定默认值。
- 不需要询问普通实现细节。

这些授权应在 Plan 阶段被纳入决策上下文。

但用户的宽泛授权不能自动覆盖真正的 L3 重大业务风险、不可逆操作和明确要求确认的事项。

# 五、Execution Plan 数据模型

需要设计正式的结构化 Execution Plan。

不能只生成 Markdown 计划文档。

Execution Plan 必须是 Workflow Core 可以校验、持久化、执行和恢复的数据结构。

建议包含以下内容：

```yaml
plan:
  id: string
  version: integer
  title: string
  objective: string
  project_context: {}
  scope:
    included: []
    excluded: []

  assumptions: []
  decisions: []
  risks: []

  clarification:
    required: []
    resolved: []

  nodes:
    - id: string
      name: string
      description: string
      type: agent
      agent:
        adapter: string
        role: string
      dependencies: []
      inputs: {}
      expected_outputs: []
      acceptance_criteria: []
      retry_policy: {}

  acceptance_criteria: []
  delivery_requirements: []

  metadata:
    created_at: string
    updated_at: string
    created_by: string
```

以上是逻辑结构示例，具体字段应结合当前代码设计，不要机械照搬。

## 5.1 Plan 校验

确认前必须验证：

- Plan 基本字段完整。
- 目标和范围明确。
- DAG 无环。
- 所有依赖节点存在。
- 不存在无效依赖。
- 节点输入输出定义合理。
- Agent Adapter 存在或有明确的后续处理方式。
- 每个关键节点有验收标准。
- 最终验收标准可验证。
- 不存在未解决的 L3 Clarification。
- Plan 中的假设和决策有记录。

校验失败时不得进入 Execute。

## 5.2 Plan Snapshot

Plan 确认后必须生成不可变的 Plan Snapshot。

要求：

1. 每次确认生成独立版本。
2. 保存完整计划内容。
3. 计算稳定内容 Hash。
4. 记录确认时间和确认人。
5. Workflow 创建时绑定 Snapshot ID 和版本。
6. Workflow 执行时读取对应 Snapshot。
7. 禁止直接修改已确认的 Snapshot。
8. 后续计划变化必须生成新版本。
9. 保留历史版本，能够追溯每次计划变更。

Plan Snapshot 是 Planning Layer 与 Workflow Core 之间的正式契约。

# 六、Plan Change Request — 执行期间计划变更

执行过程中可能发现：

- 原需求理解存在错误。
- 原技术方案不可行。
- 新发现的代码依赖导致任务范围变化。
- 数据结构或 API 设计必须调整。
- 原 DAG 缺少必要节点。
- 新增工作会影响已经完成的节点。

不能因此直接让 Agent 修改已确认的 DAG。

引入最小化的 Plan Change Request 机制。

建议流程：

```text
Agent discovers issue
        |
        v
Create Plan Change Request
        |
        v
Analyze impact
        |
        +----> Low-risk local adjustment
        |          |
        |          v
        |     Record decision
        |          |
        |          v
        |       Continue
        |
        +----> Major change
                   |
                   v
             HITL Decision
                   |
                   v
              User Response
                   |
                   v
             Update Plan
                   |
                   v
          Generate New Snapshot
                   |
                   v
          Validate Dependencies
                   |
                   v
                Resume
```

规则：

### 低风险调整

- 不改变核心业务目标。
- 不改变重要接口契约。
- 不扩大用户明确限定的范围。
- 不影响已完成节点的正确性。
- 不引入不可逆副作用。

可以由 Core 支持受控调整，记录原因和变更内容。

### 重大调整

涉及以下任意情况时必须进入 HITL：

- 业务目标变化。
- 核心需求范围变化。
- 重大数据库结构变化。
- API 契约变化。
- 重大兼容性问题。
- 已完成节点需要返工。
- 新增明显的成本或风险。
- 可能产生不可逆副作用。

用户确认后：

1. 生成新的 Plan Version。
2. 生成新的 Snapshot。
3. 重新校验 DAG。
4. 分析受影响节点。
5. 保留未受影响的已完成节点。
6. 仅重新执行真正需要变更的节点。
7. 保留完整变更历史。

本次不需要实现复杂的通用 DAG 编辑器，也不需要做可视化计划编辑器。

# 七、Agent Adapter 和 Planning Agent

Planning Layer 不应该与 Claude Code 强绑定。

需要设计可扩展的 Planner 接口。

建议职责：

- 接收用户目标和上下文。
- 执行仓库调研。
- 生成需求分析。
- 识别关键不确定性。
- 执行 Decision Policy。
- 生成结构化 Execution Plan。

当前优先复用已有 ClaudeCodeAdapter 能力。

要求：

1. Planner 与具体 Agent Adapter 解耦。
2. 不在 Planning Layer 中硬编码 Claude CLI 命令。
3. 不新增第二套 Agent 进程生命周期管理。
4. 尽量复用现有 Adapter、进程管理和执行记录能力。
5. 保留后续接入 Codex 等 Agent 的能力。
6. 不要求本次实现 Codex Adapter。
7. Planner 的输出必须经过 Schema 和规则校验。
8. 不允许模型直接写入 Workflow Core 状态。

如果当前 Adapter 契约无法合理支持 Planning，需要通过最小扩展解决，不要重构整个 Agent Adapter 层。

# 八、CLI 交互

本次优先实现可运行的 CLI，不实现 Web UI。

在现有 CLI 基础上扩展 Plan 能力。

命令名称和参数可以结合现有 CLI 规范调整，但至少支持以下能力：

```bash
devflow plan create "<研发目标>"

devflow plan show <plan_id>

devflow plan clarify <plan_id>

devflow plan answer <plan_id> <question_id> "<用户回答>"

devflow plan validate <plan_id>

devflow plan confirm <plan_id>

devflow plan snapshot <plan_id>

```

同时支持从已确认 Plan 启动现有 Workflow：

```bash
devflow workflow start --plan <plan_id>
```

如果现有 CLI 命名体系不同，保持现有风格即可。

要求：

- Plan 阶段支持用户交互。
- 能够查看调研结果。
- 能够查看待澄清问题。
- 能够查看推荐方案。
- 能够查看完整 DAG。
- 能够查看验收标准。
- 能够查看 Plan Snapshot。
- Execute 阶段继续使用现有 CLI。
- 不得为 Plan 单独建立另一套 CLI 框架。

命令行应当简洁，避免大量复杂参数。

# 十、执行期间的交互边界

必须明确 Plan 和 Execute 的交互差异。

| 行为 | Plan 阶段 | Execute 阶段 |
|---|---|---|
| 需求调研 | 允许 | 不重新完整调研 |
| 用户澄清 | 允许 | 重大问题走 HITL |
| 普通技术选择 | 自主决定 | 自主决定 |
| 计划确认 | 必须 | 不重复确认 |
| DAG 生成 | 负责 | 使用已确认 DAG |
| DAG 修改 | 可生成新版本 | 通过变更流程 |
| 普通执行细节询问 | 不建议 | 禁止 |
| 重大业务决策 | 澄清 | HITL |
| 失败恢复 | 不适用 | Core 负责 |
| 最终验收 | 定义标准 | Verifier 执行 |

特别强调：

**Plan 阶段可以问问题，但不能过度询问；Execute 阶段不能因为普通实现细节向用户提问或暂停。**

如果配置了 DingTalk 等 HITL Provider，执行期间需要人工处理的问题必须通过 Provider 通知，并保留自动恢复能力。

但本次 DF-018 不要求实现 DingTalk、ZenTao、Jenkins 等具体 Provider。

# 十一、测试和验收标准

必须通过自动化测试证明功能，不允许仅以文档或代码审查作为完成依据。

## 11.1 Planning Layer 测试

至少覆盖：

1. 明确需求直接生成 Plan，不产生多余问题。
2. 普通技术细节自动决策。
3. L2 不确定性采用推荐方案。
4. L3 重大问题进入 Clarification。
5. 用户回答后能够继续规划。
6. 同一问题不会反复询问。
7. 已经从代码或文档推导出的内容不会重复提问。
8. 多个 L3 问题能够批量展示。
9. 没有 L3 问题时能够直接进入 PLAN_READY。
10. Plan 生成失败能够恢复或重新生成。

## 11.2 Execution Plan 测试

至少覆盖：

1. Plan Schema 校验。
2. DAG 环检测。
3. 不存在的依赖节点检测。
4. 节点输入输出校验。
5. 验收标准完整性校验。
6. 未解决 L3 问题不能确认。
7. Plan Snapshot 正确生成。
8. Snapshot Hash 稳定。
9. 已确认 Snapshot 不允许被直接修改。
10. 多版本 Plan 历史正确保存。

## 11.3 Plan / Execute 集成测试

至少覆盖：

1. 创建 Plan。
2. 完成仓库调研。
3. 产生澄清问题。
4. 用户回答。
5. 生成最终 Plan。
6. 用户确认。
7. 生成 Plan Snapshot。
8. 根据 Snapshot 创建 Workflow。
9. Workflow 节点与 Plan DAG 一致。
10. 多 Agent 节点正常并行。
11. Verifier 按 Plan 验收标准执行。
12. Workflow 完成后能够追溯原始 Plan。

## 11.4 Plan Change Request 测试

至少覆盖：

1. Agent 发现低风险问题。
2. 创建变更记录。
3. 低风险调整可以继续执行。
4. 重大调整进入 HITL。
5. 用户拒绝变更时保持原计划。
6. 用户接受变更后生成新版本。
7. 新 Snapshot 正确保存。
8. 未受影响的已完成节点不重复执行。
9. 受影响节点能够重新执行。
10. 变更历史完整可追溯。

## 11.5 回归测试

必须运行：

- 全量现有单元测试。
- 全量现有集成测试。
- P0 / P0.5 回归测试。
- 多进程和租约相关测试。
- WCP 和 Recovery 测试。
- HITL 测试。
- Verifier 测试。
- 新增 DF-018 测试。

不得通过删除旧测试、跳过失败测试或降低断言来获得通过结果。

## 11.6 真实 Agent 验证

使用当前已有 ClaudeCodeAdapter 做至少一次真实 Agent 端到端验证。

建议场景：

用户提出一个范围明确但包含少量不确定性的真实研发任务。

验证：

1. Planning Agent 能够调研仓库。
2. 能识别明确需求。
3. 能识别普通技术决策。
4. 能识别真正需要用户确认的重大问题。
5. 能生成结构化 Plan。
6. 能根据用户回答更新计划。
7. 能生成 Plan Snapshot。
8. 能启动真实 Workflow。
9. 能执行 Agent DAG。
10. 能运行 Verifier。
11. 能完成最终交付。

如果本机真实 Claude CLI 认证或环境不可用，必须明确报告原因，不得用 Mock 测试冒充真实 Agent 测试。
